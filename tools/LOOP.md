# zundamstr 語尾変換 改善ループ

`zunda.js` の決定論的な語尾変換を、実データ（wss://yabu.me の kind:1 100件）に対して
「審査 → 改善 → 再測定」で回すためのループ定義なのだ。

## 前提ファイル

| path | 役割 |
| --- | --- |
| `zunda.js` | 改善対象。`zundamonize()` はアプリ本体(`main.js`)も import している唯一の実装 |
| `tools/samples.json` | 固定サンプル100件（毎wave同じものを使う＝比較可能にするため） |
| `tools/run-wave.mjs` | 現在の `zunda.js` を全サンプルにかけて `waves/wNN/output.json` を吐く |
| `tools/score.mjs` | `verdicts.json` を集計して `summary.json` / `history.json` / `test.html` を更新 |
| `tools/waves/wNN/` | wave ごとの成果物（output / verdicts / summary / zunda.snapshot.js） |

## サンプルの取り直し（通常は不要）

```sh
nak req -k 1 -l 500 wss://yabu.me > raw.jsonl
# 日本語を含み、URLのみでなく、400字以下、重複なしの先頭100件を samples.json へ
```

サンプルを差し替えると wave 間の成功率が比較できなくなるので、ループ中は固定するのだ。

## 1 wave の手順

### Step 1 — 変換を実行

```sh
node tools/run-wave.mjs <N>
```

`tools/waves/w<NN>/output.json`（`{i, src, out}` の100件）と `output.txt` ができる。

### Step 2 — 審査（並列エージェント）

100件を4分割し、4体の審査エージェントに **下の審査プロンプト** で投げる。
各エージェントは担当範囲の判定を JSON 配列で返す。返ってきた配列を全部連結して
`tools/waves/w<NN>/verdicts.json` に書く。

判定スキーマ:

```jsonc
{
  "i": 0,                    // output.json の i
  "ok": false,               // 自然なら true
  "category": "particle",    // 下記カテゴリのいずれか。ok=true なら省略可
  "reason": "「〜かしら」が未対応で「かしらのだ」になっている",
  "want": "銀行は自分には激務すぎるのだ"   // 期待する出力（任意）
}
```

カテゴリ（NG の原因分類、グラフの内訳に出る）:

- `unconverted` — 語尾がずんだもん化されずに素通りしている
- `double` — 「のだのだ」「なのだなのだ」など二重付与
- `broken` — 活用が壊れて日本語として非文になっている（例: 「食べますのだ」）
- `particle` — 終助詞・助詞の処理漏れ（かしら/よね/っけ/わよ/ね/よ 等）
- `overreach` — 変換すべきでない箇所を変換した（引用・固有名詞・体言止め・記号・英文など）
- `politeness` — 丁寧語の変換が中途半端（です/ます系の残骸）
- `other` — 上記以外

### 審査プロンプト（エージェントに渡す本文）

> あなたは日本語の校正者なのだ。「ずんだもん語尾」への機械変換の品質を審査する。
>
> ずんだもん語尾のルール:
> - 文末は原則「〜のだ」「〜なのだ」で終わる。疑問文は「〜のだ？」。
> - 体言・形容動詞語幹には「なのだ」、動詞・形容詞の終止形には「のだ」が付く。
>   例: 「猫だ」→「猫なのだ」／「食べる」→「食べるのだ」／「寒い」→「寒いのだ」
> - 丁寧語は常体に落としてから付ける。「食べます」→「食べるのだ」（「食べますのだ」は誤り）
> - 顔文字・URL・英数字・記号・絵文字・ハッシュタグはそのまま残す。
> - 体言止め、単語だけの投稿、記号だけの行は無理に変換しなくてよい（そのままで OK）。
> - 二重の「のだのだ」は誤り。
>
> 以下の各件について、`out` が「ずんだもん語尾として自然な日本語か」を判定せよ。
> 判定は語尾の自然さのみを見る。内容の是非・原文の誤字・改行位置は問わない。
> 迷ったら **自然(ok=true)** に倒す（過剰な NG は改善の信号を濁らせるため）。
>
> 出力は JSON 配列のみ。前後に説明文を書くな。各要素は
> `{"i":number,"ok":boolean,"category":string,"reason":string,"want":string}`。
> ok=true の要素は `category`/`reason`/`want` を省略してよい。
>
> 対象データ:
> ```json
> <output.json の担当スライス>
> ```

### Step 3 — 集計

```sh
node tools/score.mjs <N>
```

成功率と NG 内訳が出て、`test.html` が再生成される。

### Step 4 — 改善（改善エージェント）

`summary.json` の NG 事例を改善エージェントに渡し、`zunda.js` を編集させる。

### 改善プロンプト（エージェントに渡す本文）

> `zunda.js` の `ZUNDA_RULES` と `zundaSentence()` を改善するのだ。
>
> 直近 wave で不自然と判定された事例は以下:
> ```json
> <NG 事例（src / out / category / reason / want）>
> ```
>
> 制約（破ってはならない）:
> 1. **決定論的な純関数のままにする。** 乱数・時刻・ネットワーク・AI 呼び出しを入れない。
> 2. `ZUNDA_RULES` は上から最初にマッチしたものだけが適用される。より長い語尾を
>    より短い語尾より **上** に置く（例: 「ですか」は「です」より上）。
> 3. **回帰させない。** 直前 wave で自然だった件を壊さないこと。編集後に必ず
>    `node tools/run-wave.mjs <N+1>` を実行し、前 wave の output.json と diff を取り、
>    変化した件が「改善」であることを目視確認する。
> 4. 迷う変換はしない。変換しないで原文のまま残すほうが、壊れた日本語より良い。
> 5. `zundamonize()` の入出力シグネチャ（string → string）を変えない。
> 6. URL・顔文字・絵文字の保護ロジックを弱めない。
>
> 変更したら、何をどう直したかを1行ずつ列挙して報告するのだ。

### Step 5 — 次の wave へ

N を +1 して Step 1 に戻る。成功率が2 wave 連続で改善しなくなったら打ち切るのだ。

## 語幹表を増やすときの心得

`zunda.js` の `GODAN_STEMS` / `ICHIDAN_STEMS` に語を足すときは、
**その語幹が体言・助数詞・助詞としても使われないか**を必ず確認するのだ。
語幹表は「その仮名の直前がこの文字列なら動詞」という当てずっぽうなので、
同じ文字列が別の品詞でも使われるなら、そちらを片端から壊してしまうのだ。

実際に事故が起きた3つ:

| 足した語幹 | 壊れたもの | 症状 |
| --- | --- | --- |
| `話`（サ行） | 体言の「話」 | 「その話します」→「その話すのだ」「変な話します」→「変な話すのだ」 |
| `回`（サ行） | 助数詞の「回」 | 「3回します」→「3回すのだ」 |
| `ほど`（サ行） | 副助詞の「ほど」 | 「それほどします」→「それほどすのだ」（そもそも「ほどす」という動詞が無い） |

守ること:

1. **迷ったら入れない。** 表に無い語は無変換か既定の読みに落ちるだけで、非文は作らないのだ。
   入れて外すと語幹まで書き換わって語が消える（「できません」→「でかないのだ」）。
2. **体言と同形の語幹は位置を限る。** どうしても入れたいなら `GODAN_HEAD_STEMS` のように
   文頭だけで引く形にするのだ（体言の「話」は「その話」「立ち話」のように必ず何かの後ろに立つ）。
3. **番人は「直前が漢字」だけでは足りない。** サ行の漢語サ変よけは数字も除くのだ
   （`(?:^|[^一-龯々0-9０-９])`）。数詞の直後の1字は助数詞で、それに付く「し」はサ変なのだ。
4. **足したら必ず 3本まわす。** `node tools/grammar.mjs`（活用そのもの）、
   `node tools/regress.mjs`（実データ）、`node tools/firerate.mjs <snapshot>`（一般化）。
   grammar は落ちた0で exit 0 になるまで直すのだ。

逆に、**テ形（`て`/`で`）の直後の補助動詞は曖昧さが無い**ので安心して足せるのだ
（`〜てみる`＝上一段、`〜てくる`＝カ変、`〜ておく`＝カ行五段）。
ただしテ形の「で」は撥音便・イ音便の後にしか立たない（「読んで」「泳いで」）ので、
`(?:[んい]で|て)` まで見ないと「できます」の「で」を巻き込むのだ。

## 審査のブレ（この指標のノイズ）

審査エージェントは wave ごとに新しく立ち上がるので、**出力がまったく同じ件でも判定が反転することがある**のだ。
実測では wave3→wave4 で、出力が1文字も変わっていない3件が OK→NG に反転した（そのぶん成功率が
97% → 96% に見かけ上下がった）。**ノイズは ±3% 程度**と見るべきなのだ。

なので、成功率が下がったときは必ずこれを確認するのだ:

```sh
node -e '
const w=(n)=>JSON.parse(require("fs").readFileSync(`tools/waves/w0${n}/verdicts.json`,"utf8"));
const o=(n)=>new Map(JSON.parse(require("fs").readFileSync(`tools/waves/w0${n}/output.json`,"utf8")).map(x=>[x.i,x.out]));
const [A,B]=[3,4]; // 比較する wave 番号
const prev=new Map(w(A).map(x=>[x.i,x.ok])), oa=o(A), ob=o(B);
for(const v of w(B).filter(x=>!x.ok)){
  const same=oa.get(v.i)===ob.get(v.i);
  console.log(`#${v.i}: ${A}=${prev.get(v.i)?"OK":"NG"} 出力${same?"同一":"変化"} → ${same&&prev.get(v.i)?"審査のブレ":"実際の未修正"}`);
}'
```

**変換器が本当に悪化したか**は成功率ではなく、fixer が毎 wave 実行する
「前 wave で OK だった件の出力が変わったか」の件数で見るのだ。こちらはノイズが無い。

ノイズを減らしたいなら、1件を2〜3体の審査エージェントに独立に判定させて多数決を取るのだ
（コストは審査エージェント数に比例して増える）。
